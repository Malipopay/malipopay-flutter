# Dual authentication and safe retries in the Dart SDK

- **Date:** 2026-09-07
- **Status:** Implemented, released as 1.1.0
- **Scope:** `malipopay-flutter` only. No backend change.

## Context

The Malipopay merchant mobile app is being built on this SDK for payments,
invoices, products, customers, receipts, links, Pay Me and SMS. The app's own
`ApiClient` keeps auth, projects, KYC, go-live, wallet, settlements and
notifications, because those are app concerns rather than integrator ones.

The blocker was authentication. Malipopay backends accept two personas on the
same routes and both are first class:

1. A signed-in user acting on a project: `Authorization: Bearer <jwt>` plus
   `project: <projectId>`. The dashboard and any mobile app.
2. A server-side integration: a single `apiToken` header.

The SDK only spoke persona 2, hardcoded at `lib/src/http_client.dart:65`, with
no header hook and no interceptor list. Persona 2 cannot be used from a mobile
app: an API token is a project-wide secret, extractable from any shipped
binary, and carries no user scoping.

## Decisions

**Additive, never a replacement.** The parent CLAUDE.md is explicit that
`apiToken` support is how SDK merchants integrate and must not be dropped. The
new mode is a second constructor, and the existing one is untouched.

**Exactly one credential set per request.** The backend's middleware branches
on `apiToken` first, so sending both silently discards the JWT and acts as the
whole project instead of as the signed-in user. A `sealed class MalipopayAuth`
makes "both" unrepresentable rather than merely discouraged, and a test asserts
each mode's headers.

**Callbacks, not captured values.** A mobile app refreshes its token and
switches business without wanting a new client, so `SessionAuth` reads both
through functions on every request.

**The slug rule lives in one tested place.** The `project` header carries a
Mongo id for central-api routes and a company slug for the messaging routes
that proxy to the SMS service. That is a backend quirk, easy to get wrong at a
call site and silent when wrong, so `SessionAuth.needsSlug` owns it and is
tested against both the versioned and unversioned path forms.

## The correctness fix that came out of the audit

Every POST was retried on timeout and on 5xx, with no idempotency key. A
`/payment/collection` or `/payment/disbursement` that timed out after reaching
the backend was re-sent, and a timeout cannot tell you which side of the wire
it failed on. That is a double-charge.

The fix keeps retries where they are safe. GET, PUT and DELETE are idempotent
by definition. POST is retried only when the caller supplied a `reference`,
which is the backend's idempotency key: a repeat under the same reference
resolves to the first request rather than creating a second.

The proper fix is an idempotency-key header the SDK can mint per attempt. That
is a backend ask, recorded in `plans.md`.

## Error mapping

Malipopay puts a code label in `message` and the readable reason in `details`.
Preferring `message` is why failures read as `controller:x:y->error`. The
mapper now reads `details` first, populates `ValidationException.fields`,
treats 400 as validation (central-api returns 400 for most validation
failures), attaches the business `code` on every branch, and stops reporting a
malformed body as a connection failure.

## Verification

`dart analyze` clean, `dart format --set-exit-if-changed` clean, 60 tests
passing where there were 21. The new coverage is the package's first HTTP
testing: header selection per persona and per path, retry safety in both
directions, every error branch, and a conformance runner that executes the
shared `malipopay-sdk-tests` scenarios against a mock transport and fails if a
documented endpoint has no SDK binding.

Not verified here: a live call against UAT. That happens when the merchant app
reaches M1.
